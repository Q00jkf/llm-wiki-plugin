# 派工

> 自己做 vs 派、專長分工、交接包、防撞單、派工單格式、人力申請
> 上層：`SKILL.md`

## 1. 🔴 簡單快的自己做，複雜的一律派 —— 且平均分配

| 自己做（幾分鐘內、單一檔、無需驗證） | 派 peer（其餘一律） |
|---|---|
| 改一行指標、更新進度頁一列、跑唯讀腳本、回覆 peer | 批次改名、跨檔同步、寫腳本、逐檔盤點、開原文核對、任何要全表驗收的改動 |

- 判準不是「我會不會做」，是「**這件事會不會佔住我**」—— 主管陷進執行，就沒人做驗收與仲裁。
- **平均分配**：派工前看「Session 狀態」表，**優先派給手上無檔的 peer**；不要因某人「上次做過比較熟」連續押同一個。
  有裝像素辦公室時一併看 `office_roster`（判斷方式見 `SKILL.md`「選用：像素辦公室名單」）：誰閒置、誰被擋下，名稱可直接拿去派工。
  有裝時，派工單請 peer 呼叫 `office_profile(team=<主管的 ListAgents 名稱>)`，辦公室會把他排到 peer 區；派工結束、不再是 peer 時設 `team=off`。
- 🔑 派工比自己做貴（要交代背景），但驗收沒有替代品：peer 可互相取代，主管不能。

> 反面實例：主管一天內把清理、腳本、批次改名、進度頁全自己做，三個 peer 待命；趕執行時用了 `git add -- <目錄>`，
> 把使用者正在編輯的檔誤掃進自己的 commit。

## 2. 專長優先派工，跨界 MUST 交接

> 為什麼：兩個 peer 同一天各自改了同一份檔，各自從頭建立對同一張表的理解 —— 權責從未明確定義。

分工不用發明，**自然形成後寫進 `coordination.md` 的 Session 狀態表**，例：

| 專長 | 典型任務 |
|---|---|
| 圖面／PDF | 版本 diff、日期判讀、廢止說明 |
| Office 檔逐格改 | Excel／Word 程式化操作、全表驗收 |
| 腳本／檔案系統 | `scripts/*`、manifest、搬檔歸檔、批次改名 |

1. 專長優先；該 peer 積壓時才跨界
2. 跨界 MUST 附交接包（§3）
3. ⚠️ **名稱會變**（session 重開會改名）：**對不上時以專長欄為準**，確認身分後更新該列

🔑 另一條撞檔風險最低的切法：**範本 vs 紀錄**（空白範本／wiki／條文核對歸一邊，實際紀錄歸另一邊），物理上不重疊。
配套：**誰做的誰不驗，交叉複驗。**

---

## 3. 交接包：跨 peer 接手同一件事時，三行

> 實例：接手者得自己跑 `git status` 猜前一位收工沒。

寫進 `coordination.md` 該 peer 那列，**三行，不是報告**：
```
目標：要達成什麼（不是做了什麼）
已完成：哪些節點 ＋ 各自的結論
遺留：下一個人會踩到什麼
```
只在跨 peer 接手同一件事時寫；一般派工由派工單負責。

## 4. 🔴 派工前 MUST 確認「使用者是否已在別處交辦同一件事」

> 首次撞單：主管派 A 做某項修改的同時，使用者正在 B 那邊直接下同一個裁示。B 已完成並 push，A 若做完會產生第二份衝突版本。

1. 派工單開頭寫：**「若使用者已就此事直接交辦你，或你知道別人在做，立刻回報，先不要動手」**
2. 涉及同一份檔的派工，先列「我知道誰在動哪些檔」，讓 peer 能反駁
3. peer 收到與自己已知狀態衝突的派工 → **回報而非執行**

🔑 撞單代價不對稱：晚一輪只是慢；兩份衝突版本都有合法來源，事後查不清哪份是真的。

## 5. 🔴🔴 派工單用固定欄位，不寫散文

> 為什麼：自然語言派工 → 語義模糊 → 執行偏差。曾一天四次派工錯誤（份數、格數、日期欄位、升版 vs 就地改），
> 全部在 peer 收到後才被發現。

```
【目標】檔案完整路徑 ＋ 當前 md5／commit（逐檔列，不可寫「那兩份」）
【改什麼】座標 | 現值 | 新值      ← 逐格列。填不出來就不准發
【依據】每個新值的來源：開過哪個檔／哪條規則／使用者哪句原話
【不准碰】明確路徑（他人在編輯的、凍結的）
【自主範圍】peer 在此範圍內不得回問，直接做完回報
【必須問我】版本升不升／動到別人的檔／與既有規則牴觸／內容需自創
【回報】每完成一個階段回報一次；被權限擋下立刻傳 🔴 BLOCKED
```

🔑 `【依據】` 逼你在發出前回答「我怎麼知道的」—— 四次錯誤填到這欄都會卡住。而且比散文短。
🔴 **Token 紀律不凌駕不可逆性**：動正本、改已簽核／已被引用的內容 → 多問一趟永遠划算。

## 6. 人力申請：任務需要時主動請使用者開 session

主管**不自行開 subagent**（全域規則），但該說的時候要說。

| 情況 | 為什麼要另開 |
|---|---|
| 兩件工作檔案範圍不重疊且都在等 | 並行不撞檔 |
| 需要獨立複驗某 session 的結論 | 同一條線自我複驗價值低 |
| 現有 session 手上檔案未收尾，卻有新急件 | 硬插會把兩批改動混在同一工作區 |
| 要大量讀 PDF／新領域 | 一份 PDF 常 7–10 萬 tokens |

一句話提，不寫提案：
> 「建議再開一個 session 做 {任務}，跟 {現有 session} 的檔案不重疊；預估 token {粗估}。要開嗎？」

- MUST 附 token 粗估。開好後 `ListAgents` 取名稱 → 派工時寫明佔用範圍與回報方式 → 登記進 `coordination.md`。
- ⛔ 沒有明確不重疊的檔案範圍就不要提，否則只是製造撞檔。

# 查核

> 兩個獨立證據、複驗手段、環境層靜默破壞、因果句、偵測器上線判準
> 上層：`SKILL.md`

## 系統正確性查核＝主管最主要的產出

登記與仲裁只是手段。實證（一輪內三次）：**每一次差錯都是「回報本身有問題」，不是工作做錯。**

| 回報 | 複驗結果 |
|---|---|
| peer：檢查腳本報 ISSUES | 主管複跑 → CLEAN（另一個 session 早修掉，回報者資訊過期） |
| **主管自己**：「這是制度設計」 | peer 核原文 → 是我方自行編的，主管猜錯 |
| peer：某欄 15 列全空 | 主管比對 byte → 已填在**正本**，peer 開的是**未同步副本** |

### 1. 🔴 不採信單方回報 —— 兩個獨立證據才下結論

- peer 說「A 是 X」→ **自己跑一次**（腳本、`git status`、開檔、比 byte）或找第二個來源對照，才寫進 `coordination.md`。
- **主管自己的判斷同樣適用**：憑印象猜「本來就這樣設計」是最常見的污染源。猜的 MUST 標推測，或直接查原文。
- 回報「查無／沒有／全空」時**最需要複驗** —— 最容易因看錯位置而成立（過期副本、路徑改名、檔名不合規約）。
- 兩個來源打架時**不要選一個相信**：找出「為什麼不一樣」，那個原因通常就是真正的缺陷。

### 2. 常備複驗手段（挑對應的，不要全跑）

| 要驗什麼 | 怎麼驗 |
|---|---|
| 這份檔改了沒／回退乾淨沒 | `git status --short <路徑>`；二進位檔比 size／md5，**不相信「內容應該相同」** |
| 副本是不是最新 | 比正本與副本的 size／關鍵字次數；Office 檔**逐格**（見 07） |
| 條文／原文到底怎麼寫 | **開原文**，不讀 wiki 摘要（摘要可能是別人的推論） |
| 這個 session 是誰 | `ListAgents` ＋直接問；**名稱會過期，不得靠名稱推定身分** |
| 佔用有沒有被遵守 | `occupancy_check.py`（收尾跑） |

### 3. 環境層的靜默破壞（session 自律擋不住，要主動盯）

- **git 自動備份（obsidian-git autoCommit 之類）會突破凍結**：時間到就全掃工作區，把凍結檔＋他人未提交編輯掛上匿名 commit。
  → 改完**立刻 commit**；還原前先確認 HEAD 是否已被備份污染，必要時 `git checkout <乾淨commit> -- <路徑>` 而非 `git checkout --`。
  → 「某檔先不要 commit」是做不到的承諾：session 只控制自己的 `git add`，**只能承諾「我們不主動 commit」**。
- 🔴 **git index 全 session 共用**：`git add <明確路徑>` 只保證「我不會多加」，不保證 index 裡沒有別人加的。
  → **`git commit --only <路徑>`**；新檔先 `git add` 再 `--only` 同路徑；或 commit 前 `git diff --cached --name-only` 核對。
  > 實例：逐檔 add 九個路徑，commit 仍帶進別人 staged 的第十個檔；內容沒事，但 commit message 沒提它 → 歸屬變錯，而歸屬證據只有 commit message。
- **編輯器可能靜默改寫 `.md`**（外掛重排表格）→ 快照檔內容不等於上次寫入，動之前先讀現況。
- 🔴 **互動開啟 Office 檔＝改檔**：桌面 App 開檔存檔會正規化格式，size／md5 變、副本立刻「過期」，且被自動備份收進版本庫。
  程式化 COM 明確 `.Save()` 實測零變動。→ 順序「**先 commit → 再開檔 → 再比對**」；判準是**內容完好**，不是 byte 相同。

### 4. 🔴 因果句比數字句更需要查核

數字錯使用者可能自己發現；「**A 造成 B**」他沒有獨立資訊可驗，只能全盤採信。
> 實例：主管稱「wiki 零引用是某次清理的副作用」→ peer 拒收 → `git log -S` 零命中 → wiki 從來就沒引用過。
**好聽但沒查證的因果，不得用來佐證另一件事的效益。**

### 4b. 🔴 轉述 peer 的條文／事實 MUST 標「未親驗」

因果句往「更確定」偏、摘要往「更嚴重」偏，疊加就是「看對其實錯」。
凡未親自讀過原文的引用一律標 `（轉述／未親驗）`；peer 收到未標明者**可直接反問來源**。
peer 回報「原文沒有這句」或「原文是條件句」→ **那就是正確答案**，主管不得要求找台階。

### 5. 查核結果一律落盤

複驗發現的差異寫進 `coordination.md`（誰的回報過期／誰猜錯／為什麼不一樣），並回覆當事 session。
**主管自己猜錯時要明講並更正登記** —— 不更正，錯誤判斷會被後續 session 當事實引用。

## 6. 證據先分類，再決定驗證力度（觀察／推論／未知／偏好）

下判斷前先把每一條資訊歸類，類別決定要不要驗、驗多深：

| 類別 | 定義 | 查核義務 |
|---|---|---|
| 觀察 | 親眼讀過原文／親自跑過指令看到的結果 | 直接可用 |
| 推論 | 由觀察推導出的結論，沒有原文可直接對照 | 標「推論」，找一次反證再定案 |
| 未知 | 沒有資訊、沒查過 | 老實說「不知道」，不得用觀察或推論的語氣寫 |
| 偏好 | 使用者或主管的主觀選擇，沒有對錯 | 標「偏好」，不進查核清單——沒有可驗的東西 |

🔴 **找反證，不只是找支持**：下結論前主動想「什麼證據會推翻這個判斷」，去查那個角落，不要只驗證自己已經相信的方向。
🔑 **驗證力度配合影響範圍**：只影響一頁筆記的判斷，讀一次原文就夠；會改變規則層、動到多份卡片、或使用者要據此做決策的判斷，才值得用「兩個獨立證據」（見第 1 節）。不是所有判斷都要一樣重的查證，重的查證用在刀口上。

## 🔴🔴 新偵測器上線第一天必須讀出 🟢 —— 否則它不是守門，是待辦清單

verdict 上的數字要反映「**有人需要動手的筆數**」。沒人會動手的數字不該出現在 verdict 裡。
> 反面教材：某檢查報 66 筆，一大票是合法副本；沒有明顯動作所以永遠停在 66 → 教會所有人「verdict 可以無視」，之後新增的訊號繼承這個文化。

- **MUST**：新檢查上線讀出非綠 → 先處理或明確排除既有項目，再開啟。
- 🔑 黃燈可以存在，但 **MUST 帶到期日**。到期沒動＝死數字，拆掉或排除。判準是「有沒有到期日」不是「有沒有 owner」（有 owner 的照樣停一個月）。
- 待辦清單屬 `coordination.md`，不屬 gate。**寧可少一個偵測器，也不要一個會被無視的。**
- 做不出來的不要硬做：派工單欄位、兩個獨立證據發生在訊息裡，沒東西可掃 —— 槓桿在模板不在檢查器。
  全 repo 的 commit 歸屬偵測也不做（自動備份匿名高頻，任何檢查都被洗版）；`occupancy_check` 可行，因為它只比對**佔用表上的具名路徑**。

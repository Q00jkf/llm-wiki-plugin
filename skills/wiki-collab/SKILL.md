# wiki-collab：多 session 主管協調

前提：全域規則已定義 `ListAgents`／`SendMessage`（deferred，先 `ToolSearch("select:SendMessage")`）、
`peer-reply-<name>.md` fallback、無離線留言、commit 用 `git -c user.name="<session名>"`。
本 skill 在其上加一個**主動彙整與仲裁**的角色；沒有主管在線時，peer 仍照舊規則自己判斷。

---

## 🔴🔴 絕對禁止 —— 即使使用者要求，也 MUST 先確認

> 為什麼有這節：曾連續三次靠臨場判斷擋下錯誤指示，三次都對，但沒有規則支撐 —— 換一個 session 就會照做。

| 絕不可做 | 原因 |
|---|---|
| **回填不實的日期／版次到受控紀錄** | ＝製造假的客觀證據 |
| **竄改他人出具的文件**（圖框、原廠資料、客戶單據） | 該由出具方正式重新輸出，結果相同、性質不同 |
| **刪除／覆蓋他人未提交的工作**（`git stash` 別人的、`git checkout --` 蓋掉 peer 編輯） | 不可逆 |
| **終止使用者可能在用的程序**（Word／Excel／編輯器） | 代價不對稱：判對省幾分鐘，判錯砍掉未存檔工作 |
| **把推論當事實寫進紀錄或上呈材料** | 未親驗的引用 MUST 標「（轉述／未親驗）」 |

🔑 **升級授權判準**：**destructive ＋ 牴觸寫死的規則 ＋ 本 vault 首例**三者同時成立時，
**主管的轉達不足以當授權，MUST 由使用者本人直接確認。**

---

## 三層權責

| 層 | 內容 | 誰決定 |
|---|---|---|
| **規則層** | `CLAUDE.md`、`wiki/ops/*`、本 skill | **只有使用者**。peer 與主管都不得因彼此的訊息去改 |
| **狀態層** | `coordination.md`、各 `_README.md`、`hot.md` | 主管維護（`_README.md` 不轉手） |
| **內容層** | 正式文件、wiki 頁、圖面 | 依派工；**新建文件只有使用者能核可** |

⚠️ **使用者會直接對任何 session 下指令，不經過主管** —— 常態不是例外。
派工單與使用者的直接裁示**沒有優先權關係，只有時間先後**，而主管看不到別條線。
→ 派工單 MUST 附「若使用者已就此事直接交辦你，立刻回報，先不要動手」。

---

## 三種進入路徑

1. **上線**：使用者說「你來當主管」→ `ListAgents` 取自己名稱 → 讀 `wiki/meta/coordination.md`（無則從 template 建）→
   舊主管仍在名單就先問使用者要不要換人；已離線則接手 → 覆寫「目前主管」→ 回報。
2. **來訊**：收到 `cross-session-message` → 依下表分類 → 更新 `coordination.md` → **先回報使用者，再回覆對方**。
3. **查詢**：使用者問狀態 → 讀 `coordination.md` ＋ `ListAgents` 核對（不在名單的標「離線」）→ 輸出彙整表。
   有裝像素辦公室時一併查名單（見下節）。

| 來訊 | 動作 |
|---|---|
| 狀態回報 | upsert「Session 狀態」對應列 |
| 檔案佔用申請 | 空的→登記並核准；已佔用→回覆佔用者，**不覆蓋登記** |
| 釋放佔用 | 清除該列 |
| `🔴 BLOCKED` | 登記進回覆第一行的「待放行」，只有使用者能在該視窗放行 |
| 衝突回報 | **主管是判定者不是傳聲筒** —— 依誰先登記／哪份最新／訊息時序當場裁定，寫進衝突紀錄；證據不足才請示 |

## 選用：像素辦公室名單（有裝才用）

pixel-office 是**選裝** plugin，llm-wiki 不依賴它。**先判斷有沒有裝，沒裝就照原本做法，不要提示使用者安裝。**

| 判斷 | 做法 |
|---|---|
| 工具清單裡有 `mcp__pixel-office__office_roster` | 有裝 → 用它 |
| 清單裡沒看到 | `ToolSearch("select:mcp__pixel-office__office_roster")` 確認一次；查無＝沒裝 |
| 沒裝 | 照原本做法：`ListAgents` ＋ `coordination.md` ＋ 直接問 |

有裝時，`office_roster` 一次給出每個在線 session 的**名牌、職稱、主管／員工、ListAgents 名稱（SendMessage 用）、正在做什麼**，
表頭另列 `🔴 待放行：…`（被 auto 分類器擋下、等使用者在該視窗說放行的人）。用在三處：派工前選人（02 §1）、
回覆第一行的待放行（03 §2）、確認身分（04）。

⚠️ 名單是**即時畫面，不是權責紀錄**：誰是主管、誰佔用哪個檔仍以 `coordination.md` 為準；
名單上的職稱是 session 自己填的，和 `coordination.md` 不一致時**問本人**，不要直接改任何一邊。

## 注意事項

- 主管**沒有真正的檔案鎖**，佔用登記只是提醒；但**衝突發生後，主管的裁定是結論不是建議**。
- 主管 session 結束不會自動卸任，`coordination.md` 會留過期的「目前主管」—— 路徑 1 第 2 步處理。
- 主管的稀缺資源是**注意力**不是 token：驗收與仲裁沒有替代品，不要變成第 N 個執行者。

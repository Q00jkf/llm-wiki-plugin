> 角色分工與第一批範圍。**不要先建資料夾，先回答問題。**

> `/wiki-init` 預設只問三題（個人用、範圍清楚時夠用）。

# 導入訪談 SOP

**這是給團隊與 PM 的專案管理系統，知識庫是其中一個能力。**
訪談的目的是找出「這個團隊要用它管什麼」，不是「要收什麼知識」。

---

## 0. 先決定光譜位置

```
索引型 ←──────────────────────────────────→ 營運型
（檔案找得到就好）                          （日常工作都在這裡跑）

raw/ 掛進來、建指標卡                       專案夾有執行節點、日程有人維護
wiki/ 只是目錄                              coordination 有人看、健檢有人跑
重點：不要再找不到東西                      重點：進度與責任不會掉
一個人就能維護                              需要角色分工
```

多數團隊落在中間：**檔案資產先索引起來，挑一兩條產品線做到營運型。**
一開始就全面營運型，通常會因為沒人維護而死掉。

---

## 1. 怎麼跑這份訪談

1. 使用者說「帶我跑導入訪談」
2. 照第 2–5 節**一批一批問**（用 `AskUserQuestion`，不要一次丟 20 題）
3. 問完，對照第 6 節提出 1–2 個結構建議
4. 使用者確認後，照第 8 節動手

> 可以分幾次。把答案記在 `wiki/meta/導入訪談紀錄.md`。

🔴 **第 2 節沒答完之前，不要建任何資料夾。** 結構是答案的產物，不是預設值。

---

## 2. 階段 A — 管理對象與痛點（最重要）

| # | 問題 | 為什麼問 |
|---|---|---|
| A1 | **要管什麼對象？** 產品線／專案／客戶／部門，大概幾個？ | 決定 `raw/` 第一層與 `wiki/products/` |
| A2 | 每個對象底下，工作怎麼分？（研發／PM／品保／產線／業務） | 決定產品夾內的職能子夾 |
| A3 | 🔴 **現在最痛的是什麼？** 東西找不到／進度不透明／版本錯亂／交接斷線／稽核交不出證據 | **決定先做哪一塊。痛點沒對上，導入一定失敗** |
| A4 | 如果三個月後只解決一件事，你要哪一件？ | 逼出優先序 |

> A3 答「都很痛」時，請他挑上週真的卡住的那一次。抽象痛點做不出東西。

---

## 3. 階段 B — 團隊與角色

| # | 問題 | 對應到 |
|---|---|---|
| B1 | 幾個人會用？誰是每天用、誰是偶爾查？ | 一人 → 不必設角色；多人 → B2–B5 全要答（人的事走 `wiki-repo` 擁有者與權限） |
| B2 | **誰負責把檔案收進來**（ingest）？ | 沒有人負責＝不會有人做 |
| B3 | **誰負責維護日程**（`wiki/agenda.md`）？ | 日程是唯一真相來源，沒人維護就會出現第二份 |
| B4 | **誰負責定期健檢**（`/wiki-doctor`）？多久一次？ | 沒人跑＝規則靜靜死掉而沒人發現 |
| B5 | 有沒有人只能看不能改？ | → `wiki-repo` 的 `writable` 與寫入權限四級 |

> 多 session 主管制是**內建功能**，不是訪談題：第二個 Claude session 開起來就說「你來當主管」。
> 訪談只問人（誰維護、誰能改），不問 session。

🔴 **B2–B4 只要有一題答「還沒想」，就先別擴大範圍。** 沒有維護者的區塊會在三個月內腐爛。

---

## 4. 階段 C — 制度與既有資產

| # | 問題 | 對應到 |
|---|---|---|
| C1 | 有沒有制度要進來？（ISO／AS9100／內部 SOP／表單規則） | 制度自成一個 `raw/<制度名>/`，不要塞進產品線 |
| C2 | 制度文件是**受控紀錄**嗎？（有版次、要簽核、稽核會查） | 受控紀錄 🔴 **只能做 Tier 1 指標卡**，數值一律回正本 |
| C3 | 既有檔案在哪？大概幾份？ | → `/wiki-repo discover` 找出正確的掛載層 |
| C4 | 既有系統有哪些？（NAS／SharePoint／ERP／Notion／Git） | **決定是取代還是索引**。多數情況是索引 —— 檔案留原地 |
| C5 | 有沒有別人的 repo 要掛？你有寫入權限嗎？ | → 寫入權限四級；別人的 repo 要對方同意 |

> C4 答「想全部搬進來」時要擋一下：這套系統的預設是**檔案留在原地**，
> 搬家會製造第二份真相，而且搬完沒人維護。

---

## 5. 階段 D — 第一批與判準

| # | 問題 | 為什麼 |
|---|---|---|
| D1 | **第一批收哪一個對象？** 只挑一個 | 全面導入沒有例外都會失敗 |
| D2 | 那一批大概幾份文件？ | > 30 份就不要批次 ingest，按需單份 |
| D3 | **多久後驗收？看什麼算成功？** | 沒有判準就沒有結束，會無限拖 |
| D4 | 如果驗收沒過，要調整什麼、還是收掉？ | **先講好回退**，比事後吵架便宜 |

建議判準寫成可驗證的句子，例如：
「一個月後，PM 問『X 專案現在卡在哪』，能在 2 分鐘內從 `_README.md` 答出來，不必問人。」

---

## 6. 把答案翻譯成結構（決策對照表）

| 答案 | 結構決定 |
|---|---|
| A1 = 產品線，多條 | `raw/<產品>/`，`wiki/products/<產品>.md` |
| A2 = 有職能分工 | `raw/<產品>/{RD,PM,FAE,ProductionLine}/` |
| A3 = 進度不透明 | 重點放 `_README.md` 執行節點 ＋ `wiki/agenda.md` |
| A3 = 東西找不到 | 重點放 `wiki-repo` 掛載 ＋ 指標卡 |
| A3 = 稽核交不出證據 | 重點放制度夾 ＋ Tier 1 指標卡 ＋ `wiki/log.md` 可追溯 |
| B1 > 1 人 | 一開始就要有 `wiki/meta/coordination.md`，不要等撞車才補 |
| C1 有制度 | 制度獨立一個 `raw/<制度名>/`，`wiki/` 下開對應區（如 `qms/`）|
| C4 = 索引既有系統 | `wiki-repo add`，檔案留原地、預設唯讀 |
| D2 > 30 份 | 按需單份 ingest，不批次 |

---

## 7. 三種落地藍圖

### 藍圖一：單專案型（1–3 人，一個專案或產品）

```
raw/<專案>/{docs,data,sessions}/   ← _folder-template 複製來的
wiki/  hot / index / log / agenda / catalog
```
不設角色、不開 coordination。**最容易活下來的起點。**

### 藍圖二：產品線型（PM 視角，多條線）

```
raw/<產品A>/{RD,PM,FAE,ProductionLine}/
raw/<產品B>/...
raw/shared/
wiki/products/<產品>.md        ← 每條線一頁
wiki/projects/                  ← 跨線的專案頁
wiki/agenda.md ＋ meta/coordination.md
```
每條線一個 `_README.md` 執行節點。**PM 的主場。**

### 藍圖三：制度＋產品線型（推薦給公司導入）

藍圖二再加：

```
raw/<制度名>/                   ← ISO／AS9100／內部 SOP，與產品線平行
wiki/qms/                       ← 程序書頁、表單撰寫規則、稽核夾、records index
wiki/ops/                       ← 內部作業規則（ingest／查詢／命名／協作）
wiki/synthesis/                 ← 查核點報告、決策、競品、年報
```

> 三種藍圖都只是起點，不是規定。分法看使用者**最怕什麼混在一起**：怕產品混就按產品分、
> 怕客戶混就按客戶分、怕草稿混正式版就按狀態分。**判準只有一條：討論 A 時不該撈到 B。**
> 問完 A1–A3 再選，不要先套藍圖。

---

## 8. 確認後 Claude 要做的事

1. 跑 `init_vault.py`（先 `--dry-run` 給使用者看）
2. 把階段 A–D 的答案填進 `CLAUDE.md`：管理對象、術語、資料夾用途、查詢路由
3. B1 > 1 人 → 初始化 `wiki/meta/coordination.md`，寫上誰維護什麼
4. C3／C5 有既有資產 → 跑 `/wiki-repo discover`，**只掛第一批**
5. D1 的第一批 → 挑 1–2 份做示範 ingest，讓使用者看見成果
6. D3 的判準寫進 `wiki/agenda.md`（驗收日）與 `CLAUDE.md`
7. 訪談紀錄存 `wiki/meta/導入訪談紀錄.md`
8. `git init` ＋ 第一次 commit

### 🔴 動手前一定先確認的兩件事

1. **範圍**：只做第一批，不要順手把看到的都收進來
2. **維護者**：B2–B4 沒有指定人之前，不要建那一塊的結構

---

## 9. 導入之後

| 節奏 | 做什麼 |
|---|---|
| 每個 session 開場 | hook 自動印成熟度／整理提醒／日程窗口 |
| 每週 | 維護者跑 `/wiki-doctor`；`/wiki-repo scan` 看來源有無變更 |
| 驗收日（D3） | 對判準逐條檢查，決定擴大、調整、或收掉 |
| 規則改變時 | 寫進 `wiki/ops/rulings.md`（Why／實例／代價），`CLAUDE.md` 只留一句話 |

**想改結構隨時可以** —— `raw/` 是真相、`wiki/` 是索引，索引可以重建。
但改 `raw/` 的分類法要慎重，那會動到所有 source key。

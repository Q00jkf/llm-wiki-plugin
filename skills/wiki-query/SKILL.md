# wiki-query：查詢

先讀 `wiki-core` 的 R2（所有資訊標來源）。**查不到就說查不到，不得用訓練資料假裝。**

---

## 讀取順序（由便宜到貴，夠了就停）

```
1. wiki/hot.md          最近上下文，通常夠回答「現在在做什麼」
2. Grep 目標關鍵字       定位到哪幾頁，不要整頁讀
3. wiki/index.md        需要全局視野才讀
4. 個別 catalog 卡       需要細節才讀
5. 🔴 開正本            卡是 Tier 1 指標卡時，數值一律即時讀正本
```

---

## 🔴 指標卡不含數值

看到 `tier: 1` 或 `type: doc-index` 的卡，**它故意不放數值**。
卡上的 TOC 告訴你「答案在正本第幾節／哪個 Table」，然後你去開 `current_file` 讀。

直接引用卡上的數字 = 引用一份聲明自己不是真相來源的東西。

---

## 多產品／多 repo 防混淆

本系統常有多來源共存，且術語高度重疊。**扁平的全域 grep 會把「關鍵字共同出現」誤判成「同一個東西」。**

1. 查特定產品／專案 → `Grep` 帶 `path=` **scope 到該產品的資料夾**，不做全域 grep
2. 命中跨來源頁 → 引用前先看 frontmatter 的 `product:` / `repo:` 是否為目標
3. **不主動補充「非當前目標」的細節** —— 即使貼「別混淆」標籤也不行，端出來本身就是污染

---

## 回答格式

每個結論後面接來源：

```
{結論}　[📄 文件名, p.XX]
{結論}　[⚠️ 非資料庫：推導]
```

資料庫中找不到時：

1. 明說「資料庫中無足夠資料回答此問題」
2. 說明哪些來源可能相關（即使尚未 ingest）
3. 要補非資料庫知識 → **必須**標 `[⚠️ 非資料庫：...]`

---

## 有結構化真相來源的東西，寫腳本查，不要讀 wiki

料號、廠商、表單狀態、庫存這類**已經有 xlsx／資料夾／資料庫當真相來源**的資料：
wiki 頁一定會過期。正確做法是寫一支腳本現掃現算，放 `scripts/`。

判準：**這個問題的答案會不會因為某個檔案被改而改變？** 會 → 腳本；不會 → wiki 頁。

# wiki-query：查詢

先讀 `wiki-core` 的 R2（所有資訊標來源 —— 指 `raw/` 正本或 alias 路徑，不指 wiki 卡）。**查不到就說查不到，不得用訓練資料假裝。**

---

## 讀取順序（由便宜到貴，夠了就停）

```
1. wiki/hot.md          最近上下文，通常夠回答「現在在做什麼」
2. Grep 目標關鍵字       定位到哪幾頁，不要整頁讀
3. wiki/index.md        需要全局視野才讀
4. 個別 catalog 卡       需要細節才讀
5. 🔴 開正本            卡是 Tier 1 指標卡時，數值一律即時讀正本
```

---

## 🔴 指標卡不含數值

看到 `tier: 1` 或 `type: doc-index` 的卡，**它故意不放數值**。
卡上的 TOC 告訴你「答案在正本第幾節／哪個 Table」，然後你去開 `current_file` 讀。

直接引用卡上的數字 = 引用一份聲明自己不是真相來源的東西。

**正本是 PDF 時**：用 `Read pages="N"`（卡上的 TOC 會告訴你第幾頁）。
`offset`／`limit` 對 PDF 無效，沒帶 `pages` 的大 PDF 會被守門擋下 —— 那不是壞掉，是要你只讀那一節。
細節見 `wiki-ingest` skill 的「PDF 怎麼讀」。

## 防混淆：討論 A 時不該撈到 B

多來源共存、術語重疊（PPS、雙天線、時序、合約條款…到處都有），**扁平的全域 grep 會把
「關鍵字共同出現」誤判成「同一個東西」**，把 A 的規格答成 B 的。

**隔離軸是使用者定的，不是系統定的。** 他在 CLAUDE.md「資料夾用途」表決定 `raw/` 第一層按什麼分
（產品／客戶／部門／制度／文件狀態…）—— 那就是他最怕混在一起的東西，也就是查詢時的隔離單位。
系統不猜軸，只保證沿著他定的軸隔離。

### 系統怎麼做到隔離（三層，缺一層就會漏）

| 層 | 機制 | 誰維護 |
|---|---|---|
| ① 實體 | `raw/<第一層>/` 是不同資料夾；`Grep` 帶 `path=raw/<第一層>/` 或 `path=wiki/catalog/`＋frontmatter 過濾，**物理上撈不到別的** | 使用者分夾，系統照用 |
| ② 標記 | 每張卡 frontmatter 有 `scope:`（值＝它屬於 `raw/` 的哪個第一層，或外部 alias）；跨多個就 `scope: [A, B]`，通用的 `scope: shared` | ingest 時系統寫，`repo.py link` 補 |
| ③ 紀律 | 引用前看 `scope:` 是不是目標；**不主動端出非目標的內容**，即使貼「別混淆」標籤也不行 —— 端出來本身就是污染 | 回答時系統守 |

### 查詢步驟

1. **先定 scope**：問題裡有對象（「產品 A 的散熱規格」「甲客戶的交期」）→ 對到 CLAUDE.md 路由表的那一列。
   問題沒指對象、而 vault 有多個 scope → **問使用者要哪一個，不做全域 grep 猜**。
2. `Grep` 帶 `path=` 限定到該 scope 的 `raw/` 夾；catalog 卡命中後看 `scope:` 對不對。
3. 命中 `scope: shared` 的頁可以用，但回答時標明它是通用的。
4. 使用者明問「A 跟 B 差在哪」才把兩邊並列；否則只講 A。

> 為什麼三層都要：只靠①，跨對象的 shared 頁會漏；只靠②，全域 grep 還是會先把 B 撈進 context 再靠自制不講 —— 進了 context 就會滲；
> 只靠③，等於靠紀律，而紀律一定會被違反。

## 回答格式

每個結論後面接來源：

```
{結論}　[📄 文件名, p.XX]
{結論}　[⚠️ 非資料庫：推導]
```

資料庫中找不到時：

1. 明說「資料庫中無足夠資料回答此問題」
2. 說明哪些來源可能相關（即使尚未 ingest）
3. 要補非資料庫知識 → **必須**標 `[⚠️ 非資料庫：...]`

## 問題分流：一種問題 → 一條路，寫在 CLAUDE.md「查詢路由」表

料號、廠商、表單狀態、庫存這類**已經有 xlsx／資料夾／資料庫當真相來源**的資料：
wiki 頁一定會過期。正確做法是寫一支腳本現掃現算，放 `scripts/`，並在 CLAUDE.md 路由表登記
「問題類型 → 腳本 → 查無的條件」。

判準：**這個問題的答案會不會因為某個檔案被改而改變？** 會 → 腳本；不會 → wiki 頁。

🔴 **「查無」的條件要寫死，不然一定答錯**：

- 一支腳本 0 筆 ≠ 沒有。每支腳本只掃它管的那一種來源（採購單掃不到制度前的庫存；受控表單掃不到公司自用表單）。
  路由表要寫「兩支都跑過才能說查無」或「腳本 0 筆再 `find raw/ -iname`」，**回答時講出查了哪幾處**。
- **進度／狀態題**（「XX 到哪了」「卡在哪」）：有 `_README.md` 就讀它；沒有就**問使用者**，不讀舊狀態頁、不推論。

## 開正本要精準：用卡上的頁碼

卡的「正本各頁」表就是為了這一刻。`Read pages="N"` 只讀那一節，不整份讀。
**卡沒有頁碼表**＝當初建卡偷懶，補完再答；不要猜頁數翻整份。

## 規模超過 index 能負荷時的下一步（暫不內建，先記路線）

`hot.md → Grep → index.md → 個別卡 → 正本` 這條讀取順序在 ~100 份來源、數百頁的規模下夠用
（上游 Karpathy 的 gist 也是這樣說的）。真的長到 grep／index 開始選擇性漏東西時，
下一步**不是**直接搬某個上游的檢索程式碼（常綁死 WSL／POSIX 專屬 API 或特定 embedding 服務），
而是照這幾條設計原則自己寫一支 stdlib 腳本：

- 段落分塊，每塊帶著頁面標題／frontmatter 摘要當前綴（BM25 對「已加上下文的文字」打分，不對裸段落）
- 索引是可拋棄的衍生物，放 `wiki/meta/` 或等價位置，**不進 wiki 正文**、壞了就刪掉重建
- 索引缺失或損毀 → 明確退回現有的 `Grep`／`log_index.py`，不要假裝有結果
- 🔴 **檢索結果不是證據**——命中的段落只負責「告訴你去讀哪一頁」，答案仍要回正本；這條與 R1 同精神

在真的出現「找不到頁」的具體案例之前，這段只是路線紀錄，不用預先實作。
